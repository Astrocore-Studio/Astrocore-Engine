# ADR-0017. Постоянный идентификатор игрока и стадия подключения

Дата: 2026-11-27. Статус: принято (фаза 6, задача 6.1 плана Build).

## Контекст

База данных SS14 (игроки, профили, баны, журнал) строится вокруг `NetUserId` — GUID игрока.
В Robust он появляется до входа: с аккаунтом — от сервера авторизации, без него — от
контента (`AssignUserIdCallback`: SS14 хранит пары «имя → GUID» в базе), иначе — случайный.
Затем Robust поднимает асинхронное событие `Connecting`: контент проверяет баны, белый список,
заполненность сервера и может отказать (`Deny`) — это ждёт ответа базы и не тормозит такт.
Если тот же пользователь уже на сервере, старое соединение выбрасывается.

У нас сессия создаётся сразу по приветствию клиента, и у неё есть только имя. Авторизации
аккаунтов пока нет (задача 8.4).

## Решение

1. **`NetUserId`** — UUID в `Session::user_id`.
2. **Стадия подключения.** Приветствие с верным набором компонентов поднимает
   широковещательное `PlayerConnecting { conn, name, address, denied, deferred }`. Обработчик
   может отказать сразу (`denied`) или отложить решение (`deferred`). Тогда соединение ждёт, его
   пакеты не обрабатываются, а игра потом вызывает `complete_connection(conn, Ok(user_id) |
   Err(причина))` — так ответ базы приходит без блокировки такта. Без отложенного решения
   игрок получает случайный `NetUserId` (гость Robust).
3. **Отказ** — сообщение `Rejected` с причиной; дальнейшие пакеты соединения не
   обрабатываются. Разрыв соединения на уровне транспорта — вместе с выбросом игрока
   администратором (6.6).
4. **Тот же пользователь** — прежняя сессия получает `Rejected` и закрывается до создания новой.

## Последствия

- Игра решает, откуда берётся `NetUserId` и кого не пускать, как контент SS14.
- Когда появится авторизация (8.4), идентификатор аккаунта придёт до `PlayerConnecting`, а
  выдача по имени останется для гостей.
