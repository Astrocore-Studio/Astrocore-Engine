# Сохранения

Модель: **снимок + журнал**.

```
data/
├── snapshot.json    контрольная точка (атомарно: tmp → fsync → rename)
└── journal.jsonl    операции после снимка: "<crc32 hex> <json WorldOp>\n"
```

* `Store::save_snapshot` пишет снимок и очищает журнал. Сбой между `rename` и очисткой
  безопасен: повтор журнала пропускает уже учтённые операции (идемпотентность по `seq`).
* `Store::append` пишет операцию с `sync_data`.
* `Store::recover` = снимок + повтор журнала.

## Недоверенные данные

Снимок проходит: проверку `format_version` и миграции → разбор → `World::from_state`
(полная валидация) → сверку ревизии → сверку `content_hash`. Журнал: CRC каждой
строки; оборванная **последняя** строка (сбой при записи) отбрасывается и
отмечается в отчёте; повреждение **в середине** — ошибка; пропуск `seq` — ошибка;
операция, не применимая к снимку, — ошибка. Журнал без снимка не принимается.

## Резервные копии

`Store::backup(метка)` копирует снимок и журнал в `backups/<метка>` через временный каталог и
переименование; `list_backups`, `prune_backups(N)`, `restore_backup(метка)` — восстановление
проверяет копию (`recover`) **до** замены рабочих файлов, поэтому повреждённая копия ничего не
портит. `Store::with_auto_backup(N)` после каждого снимка делает копию `snap-<ревизия>` и хранит N
последних; сервер включает это флагом `--backup-keep N`.

## Обновление авторской карты N → N+1

`astrocore_persistence::upgrade::upgrade_map(base, new, runtime, policy)` — трёхстороннее
слияние: автор изменил карту `base → new`, игроки — `base → runtime`. Правки автора переносятся
в рабочий мир обычными командами (с валидацией и ревизиями, `ObjectId` сохраняются); работа
игроков не теряется. Конфликты попадают в отчёт: оба изменили объект, автор изменил убранное
игроками, автор убрал изменённое игроками, новое не помещается на месте построек игроков,
изменение определения этажа (онлайн не применяется), удаление непустого этажа. Политика
`KeepRuntime` (по умолчанию) оставляет серверную версию, `PreferAuthor` берёт авторскую; в обоих
случаях решение записано в отчёте. Операции обновления возвращаются списком для журнала и
рассылки; повторное применение ничего не меняет. Из командной строки:
`astrocore-tools upgrade-map --base N.acproj --new N+1.acproj --data-dir <каталог> [--prefer-author]`.

## Миграции

`Migrator`: шаг `from` переводит документ версии `from` в `from + 1`. Текущая версия
формата — 1, шагов пока нет. Правило: **любое** изменение схемы = новая версия +
шаг миграции + golden-файл старой версии (`crates/astrocore-persistence/tests/golden_snapshot_v1.json`,
тест `golden_v1_snapshot_still_loads`). Генератор golden-файла: тест
`generate_golden` (`--ignored`), запускать только осознанно.
